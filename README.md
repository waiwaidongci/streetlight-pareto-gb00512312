# 路灯暗区报修集中度

用路灯台账补齐零报修点位，按工单集中度和每百盏报修数安排夜巡。

临汀市照明养护中心的 12 人调度与夜巡班组，负责滨河、老城两片区的道路照明。 值班员从 GIS 导出台账中的灯组和在册灯具数，从市政热线导出已归并的暗区事件工单。此前在表格透视工单，再人工查灯具数和点位。现在按灯组编号关联两份明细，分析员在灯组与工单页导入明细并发起测算，复核主管在夜巡复核页核对工单、登记处置。只读人员查看已发布结果和交付清单。

- 工单透视表只含报过修的灯组，跨片区比较时会漏掉零报修点位。
- 只按工单总数排班容易错过灯具少、重复报修密集的点位。
- 夜巡交接时缺少灯组编号和工单号，现场会重复查地图和热线系统。

## 演示流程

1. 11 月 21 日 16:30，从 GIS 和热线导出当期台账及 11 月 14–20 日已归并的暗区事件工单。
2. 在「灯组与工单」导入「临汀路灯暗区报修_20261114-20.csv」，核对 10 个灯组和 20 张工单。
3. 在「集中度测算」运行 11 月 14–20 日全片区分析，设置头部 20%、至少 2 单、每百盏至少 40 单。
4. 在「集中度与巡检队列」核对 5 个零报修灯组仍在分母内，头部 2 组占 65%，基尼系数为 0.67。
5. 对照巡检队列，老城东门巷 LH-02 有 5 单、5 盏，滨河长堤辅道 LH-04 有 2 单、3 盏，安排同班夜巡。
6. 沿用同一日期，指定滨河片区并改看头部 40%，复核前 2 组共 12 单、片区共 14 单。
7. 在「夜巡复核」记录安排夜巡的灯组编号和夜班交接事项，18:00 从「巡检交付」导出结果给养护班组。

## 断点诊断演示流程

1. 在「接线和开关」核对首批记录：1 个电源、8 条线路、1 个断开的开关、6 个灯组和 5 条同一时段的夜巡观测（LH-04 当班漏记）。
2. 在「断点测算」用首批批次发起测算，默认断点上限 12 处、单轮 50 秒。
3. 在「断点诊断」核对结果：最少 3 处断点，共 2 套最优方案；SEG-03、SEG-04 每套方案都含，SEG-06、SEG-07 仅部分方案出现。
4. 展开「可复算方案 · 方案一」逐灯核对来电路径和切断断点，再用「复算工具」任选断点组合验证，例如只勾 SEG-03、SEG-04 会看到 LH-05 与观测不符。
5. 在「接线和开关」切换到补录批次（补登 LH-04 为亮），另起一次测算：LH-03 的灭与 LH-04 的亮无法同时成立，结果页指出至少舍弃 1 条观测（LH-03 或 LH-04）才能算通，并给出舍弃后的断点方案作证。
6. 补录只影响新发起的测算；进行中的测算即使超时续算，也仍按发起时的接线、开关和观测快照恢复，已排除的断点组合不会重查。

## 计算口径

- 每个在册灯组填一条台账行，填写片区、点位、灯具数。每个已归并事件填一条工单行，填写工单号和报修日期。两类行共用灯组编号，编号去除首尾空格并转为大写。先关联全量记录，再按片区和含首尾的报修日期筛选。日期筛选保留所选片区全部在册灯组。
- 每组的有效工单数记为 x。升序排列后，洛伦兹曲线在 i/n 处取前 i 组工单数之和除以总工单数 S，含原点。基尼系数用全部 n 个排名计算，即 Σ[(2i−n−1)xᵢ]/(nS)，其中 i 从 1 开始。
- 帕累托排名按工单数降序，同数按灯组编号升序。头部 p% 取向上取整的 n×p/100 个灯组，份额为这些组工单数除以 S。两个图按组数每 5 个百分点线性插值，表格提供逐组排名及累计份额。
- 每百盏报修数为 100×组工单数/在册灯具数。重复单数和每百盏门槛同时达到才派夜巡；派巡队列按未四舍五入的每百盏报修数、工单数降序，再按灯组编号升序。其余有工单的点位继续观察，零工单点位常规归档。
- 空台账、无匹配片区、倒置日期、重复编号、未匹配工单、非正整数灯具数都会报错。有效范围内零工单时，保留灯组与归档结论，基尼和报修份额留空。相同明细和参数可复现结果；是否存在照度不足由夜巡现场确认。

## 断点诊断口径

- 接线记录分电源点、线路、开关、灯组、观测五类，编号和节点去除首尾空格并转为大写。开关登记在线路上，一条线路一个开关；每个灯组在同一时段只记一条观测，漏记的灯组可补录为新批次。
- 开关闭合且未断的线路导电。灯组节点与任一电源节点连通即为亮：灯组只要还有一路来电就算亮。
- 候选断点只取落在到来灭灯组路径上的线路，并先排除单独断开就会误伤亮灯组的线路。按断点数递增枚举，找到的第一层即最少断点，并枚举该层全部最优方案。求解超时自动保存进度排队续算，已排除的组合不重查。
- 全部最优方案取交集得「每套方案都含」的断点，在并集中但不在交集的为「仅部分方案」。方案一附逐灯复算明细：亮灯给出来电路径，灭灯给出切断全部来路的断点；结果页的复算工具可按发起时的快照核对任意断点组合。
- 全部候选搜完仍无解时，按舍弃条数递增找出至少舍弃哪些观测才能算通，并给出舍弃后保留观测的最少断点方案作证。断点搜索上限低于候选线路数时，上限内无解只提示提高上限，不断言无解。
- 发起测算时对接线、开关和观测做快照。补录只供新测算，中断后恢复仍按发起时的接线、开关和观测续算。

## 本地开发

| 组件 | 实现 |
|---|---|
| 前端 | Nginx 与原生 HTML、CSS、JavaScript。`frontend/src/pages` 放页面，`components/common` 放共用表格、图表及表单。 |
| API | Python 3.11、FastAPI、SQLAlchemy。`backend/src/domain` 放本项目字段、业务计算和演示数据，`routes` 放接口，`models` 放表模型。 |
| 后台 | 独立 Python worker，通过 Redis 唤醒，从数据库租约领取计算，CSV 写入共享卷。 |
| 数据 | PostgreSQL 16 存储批次、运行与审计。`backend/scripts/seed_demo.py` 可安全重复执行。 |

改动前端后执行 `docker compose up -d --build frontend`。改动接口或算法后执行 `docker compose up -d --build backend worker`，再刷新浏览器。如需保留数据，停止时执行 `docker compose down`。使用 `docker compose down -v --remove-orphans` 会清除该项目的数据库、Redis 和报表卷。

`.env.example` 中的 `COMPOSE_PROJECT_NAME`、`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT`、`APP_SUBNET` 控制项目隔离。`DB_PASSWORD`、`JWT_SECRET` 和 `SEED_DEMO` 为本机演示默认设置。后端 `constants/enums.py` 与前端 `src/constants/enums.js` 保持角色、运行状态和复核状态一致。项目许可证见 `LICENSE`。
